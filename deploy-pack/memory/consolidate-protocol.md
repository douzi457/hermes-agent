# 记忆整理规程（M3）

执行者：值班 Job 04（memory-consolidate），每晚一次；人工整理时同样按本规程。
前置输入：`memory_health.py` 对 `$HERMES_HOME/memories` 的当次报告 +
MEMORY.md / USER.md 全文。只看脚本报告不读全文，不许下判定。

## 一、体检报告怎么读

| 报告段 | 含义 | 规程动作 |
|--------|------|----------|
| 占用 ≥80% | 离撞墙不远了 | 本轮必须降级/归档腾出至少 10% |
| 占用 ≥95% | 写入随时被拒 | 先腾位再做其他整理，摘要里标红说明 |
| 规范化后完全相同组 | 实锤重复 | 直接合并，保留一条 |
| 高相似条目对 | 疑似重复或新旧两版 | 逐对读原文判定：合并 / 新替旧 / 两条都留（并在摘要注明为何都留） |
| 无日期条目 | 违反写入纪律 | 能判定日期的补上；判定不了的降级进 journal |
| 超 90 天未动 | 可能已失效 | 逐条复核：仍成立的在条目尾更新复核日期；失效的归档；判不准的进待裁决 |

## 二、四种处置的判定标准

- **合并**：同一事实的多个版本 → 合成一条，取信息量最大、日期最新的表述；
  被合并掉的版本原文追加进当日 journal（留痕，不蒸发）。
- **新替旧**：同一事项新旧冲突 → 以新为准改旧条本身（用 `memory` 工具的
  patch/replace，不许 add 一条新的并存）；旧表述沉 journal。
  判定「谁新」看条目日期；日期相同或无日期时看是否能对应到某次明确纠正，
  对不上就进待裁决，不许猜。
- **降级**：细节性、一次性、过程性内容（某次任务的具体参数、当时的临时安排）
  → 移到 journal 对应日期文件，长期层只留一句结论（若结论本身有长期价值）。
- **归档**：已失效且无保留价值（过期的安排、已被替代且 journal 已留痕的旧版）
  → 移入 `memories/archive/<YYYY-MM>.md`，条首注明归档日期与原因。

## 三、待裁决规则

疑似矛盾但无法判定谁对谁错的，一律不删不改，原样列入变更摘要的
「待用户裁决」区：写明两条原文、各自日期、你的倾向与理由，等用户一句话。
连续两周无人裁决的，在周体检报告里再次置顶提醒，不许自行了断。

## 四、《记忆变更摘要》格式（产出物，写进 duty/drafts/<日期>-memory.md）

```markdown
# 记忆变更摘要（YYYY-MM-DD）
- 整理前：MEMORY x 条 / y 字符（占用 z%）；USER x 条 / y 字符（占用 z%）
- 整理后：MEMORY x 条 / y 字符（占用 z%）；USER 同上
- 待批条数：n（write_approval 开启时，后台写入在待批区的数量）

## 合并（n 组）
- 「<合并后条目首句>」← 由 #a、#b 合并，旧版已沉 journal

## 新替旧（n 条）
- 「<事项>」：<旧结论> → <新结论>（依据：<日期/来源>）

## 降级（n 条）/ 归档（n 条）
- 「<条目首句>」→ journal / archive，原因一句

## 待用户裁决（n 对）
- A「…」（日期） vs B「…」（日期）；倾向：X，理由一句
```

## 五、纪律

- 整理前后各一次 git 提交（命令见 Job 04 提示词），是本规程的一部分不是可选项。
- 一轮整理只动确有把握的条目；拿不准的宁可进待裁决，不许为了「报告好看」多合并。
- 摘要里的每个数字必须来自体检脚本或 git 记录，不许估算。
- 整理失败（git 不可用、工具报错）时停手并在摘要里写清失败点，按 duty-officer
  的失败上报规程处理。
